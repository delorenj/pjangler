# pjangler

Project definitions now live in repository `.project.json` files with one case-insensitive `project_id`. Use `pj info`, `pj list`, and `pj doctor`; the singleton PostgreSQL registry indexes those manifests. See [project registry](docs/project-registry.md) for installation, migration, and compatibility details.

Project subsystem bootstrapper CLI + MCP server.

Ticket boards: `plane` and `trello` are supported. `.project.json`
`ticket_provider.type` is the authority for board reads and writes; a missing
binding or a historical `linear` value is not silently interpreted as Plane.
`pj board provider` prints the bound supported type, while unsupported bindings fail
before adapter/network use. Shared board links use Plane issue URLs only for
Plane and `https://trello.com/b/<board-id>` for Trello; missing boards yield no
link. Existing Trello operations remain limited to what its adapter implements.

## Install

Requires Node 24 or newer. `pj skills` runs the `skillex` CLI on PATH
(`npm:@delorenj/skillex` via mise); see
[the integration contract](docs/skillex-integration.md).

```bash
git submodule update --init --recursive   # templates/commonproject; a plain clone leaves it empty
npm install
npm run build
```

`npm test` (scripts/run-tests.mjs) needs that submodule: the `check:submodule-checkout`
gate fails with the init command when `templates/commonproject` is empty. The
Postgres-backed suites read the standard `PG*` variables; point them at a
disposable server (CI uses a `postgres:16` service). `PJANGLER_REQUIRE_DISPOSABLE_POSTGRES=1`
makes a missing postgres/psql/bun fail instead of skip, as CI does.

## CLI usage

```bash
npm run build
node dist/index.js --help
# or if installed globally
pjangler --help
```

## Repository ignore contract

CommonProject preserves an existing `.gitignore` and adds only portable
project rules for secrets and local `.agents` projections. It never copies the
operator's `core.excludesFile`. `.agents/` is the sole canonical agent-config
tree; `.claude/`, `.codex/`, and the other supported client roots are generated
local projections covered by machine-wide ignore policy. `bmad.cli-roots`
removes only exact obsolete lines previously generated by pjangler and never
changes Git's index. Use the `gitignore-maintenance` skill to audit effective
rule provenance and reconcile already-tracked ignored paths.

## Project notebook

`pjangler notebook` manages one companion Open Notebook for a registered
repository. The binding and stable Overview note IDs live in `.project.json`
and the project registry; endpoint, authentication mode, defaults, and finite
capture limits live in the registry's global `notebook` configuration.

```bash
pjangler notebook status . --json
pjangler notebook create . --live --json
pjangler notebook list notes . --json
pjangler notebook search notes "release evidence" . --json
pjangler notebook audit . --json
pjangler notebook migrate . --live --apply --json
```

True `SessionStart` and `SessionEnd` hooks are projected separately from the
project-scoped hook masters. Their per-repository policy stays fail-open and
disabled until explicitly enabled in `.project.json`.

## Parity audit

BMAD recipes support an optional owner-provided g33 companion for registered
33GOD projects, with explicit opt-in/out, no-write previews, and structured
optional outcomes. See [g33 companion](docs/g33-companion.md) for the callable
configuration and the actual `pj recipe run bmad --dry-run --json` commands.

`pjangler audit` runs the deterministic 33god parity rules against a repository
and exits nonzero when any of them fails. `pjangler migrate` applies the
idempotent fix the owning rule declares.

```bash
pjangler audit                                          # every rule, human report
pjangler audit --json                                   # machine-parseable
pjangler audit --rules mise.config-root,sot.project-json
pjangler migrate sot.project-json --dry-run
pjangler migrate --all
```

`--rules` reports only the rules you name. An unknown id is an **error, never an
empty pass** — a caller probing for one rule learns that the rule is gone
instead of reading a clean report over nothing.

`pjangler audit --json` and the `pjangler_list_parity_rules` MCP tool report the
live catalog. The rules are owned by the recipes in `src/recipes/`, not by a
central table, so that catalog is the only authority on which ones exist.

## Obsidian plugins

`pjangler init <name> --obsidian-plugin` does everything a normal init does
(registry, `.project.json`, board, BMAD, skills, hooks, mise, the init commit).
The difference is the CommonProject render: it is the variant built on the
canonical [obsidian-sample-plugin](https://github.com/obsidianmd/obsidian-sample-plugin).
That means `manifest.json`, `versions.json`, npm + esbuild + TypeScript in `src/`,
`eslint-plugin-obsidianmd`, and build/release workflows on the self-hosted runners.

```bash
pjangler init tag-wrangler --obsidian-plugin --description "Wrangle tags across a vault"
cd tag-wrangler && npm install && npm run dev
mise run plugin:link ~/Vaults/Main   # symlink into <vault>/.obsidian/plugins/<id>
```

- The type is recorded as `template.commonproject.project_type` and in
  `.copier-answers.yml`. It is fixed at creation, and re-running `init` keeps it.
- On an existing repo, the flag only records the type, and only when the repo
  already has an Obsidian `manifest.json`.
- `mise run version:bump` keeps `package.json`, `manifest.json` and `versions.json`
  in step. It never tags. Release with `npm version patch|minor|major`, which
  commits and then tags a bare `X.Y.Z` (Obsidian matches that), and push the tag.
- MCP takes the same choice as `projectType: "obsidian-plugin"` on
  `pjangler_project_init` and `pjangler_bootstrap_33god_project`.

## Agents

pjangler does not hire, provision, or inspect agents. That is Flume's surface —
`flume hire`, `flume roster`, `flume record`, `flume review` — and the org chart
is Flume's record.

`pjangler describe` still reports a repository's employees, and `pjangler init`
carries existing `.project.json` `agents` entries forward. Neither writes a new
one: that block is a one-way projection of the org chart, not a place a project
declares intent.

## Orienting in a repo

`describe` reads a repo and reports what it actually is — detected type,
installed subsystems, config files present, and what to do next. It is the
first call for an agent (or a human) landing somewhere unfamiliar, and it works
in any repo, 33GOD or not.

```bash
pjangler describe                # current directory
pjangler describe ../some-repo
pjangler describe --json         # machine-parseable, for agent context
pjangler describe --interactive  # tick off fixable findings, press A to apply
```

Subsystem presence and subsystem correctness are reported separately: presence
comes from marker files on disk, parity from the recipe's own audit rules. A
subsystem that was never installed reads `absent`, not `broken`.

### Last activity, not lifecycle status

Projects report **when work last happened**, not a lifecycle word. The old
`status` field said `planned` for 22 of 27 registered projects — including ones
with commits the same day — so it never varied and never informed.

Activity is computed from git at read time, so it cannot go stale and no cron
has to walk the registry. It spans more than the checked-out branch:

| source | covers |
| --- | --- |
| refs | every local branch, remote-tracking branch, and tag |
| worktrees | every linked worktree's HEAD, including detached ones whose commits are on no ref |
| uncommitted | working-tree edits that are not committed yet |

The newest of those wins, and the winning source is always reported. Remote
state reflects your last fetch — nothing here touches the network.

`pj list` orders by that signal, newest work first.

## Shell prompt

`pjangler-prompt` prints one compact line when the working directory is inside a
pjangler project. Outside every project it prints nothing, except in a zellij
pane, where it prints the pane's crank segment alone: crank mode belongs to the
pane, not the project.

```
pjangler (PJAN) · ⚙ develop · 3m · @pjangler_pm_bot(PM) id v1 6/6 · 🍬 3/124 · ⚡ crank ↑3d4h ↻5m ⏳2m
```

Right after the slug and board prefix comes the project's declared MODE, then
the age. The mode is the owner's `mode:` key in the repo's committed
`.launch.yaml` (agents never edit that file), read inline on every prompt — a
tiny file, never cached, never thrown on:

- `⚙ develop` — the default: no `.launch.yaml`, `mode: develop`, or the legacy
  alias `mode: steady`. An unknown or broken declaration also reads as
  `develop`, exactly as the launch-pass monitor reports it.
- `🚀 launch` — racing a finish line (the launch pass is active).
- `✨ polish 12↑ 5✓ 31⟳` — around-the-clock exploratory QA; the numbers come
  from the pass's ledger at `agents/hermes/pm/runtime/polish-metrics.json`:
  improvements proposed ↑, implemented ✓ and total QA cycles ⟳
  (`len(proposed)`, `len(implemented)`, `cycles`). A missing or broken ledger
  shows `✨ polish` alone — the mode is known even when its metrics are not.
- `● live` — the product is in production (a lifecycle stage, no pass).

The segment is always shown inside a project, develop included; the
crank-only line outside projects has no mode.

After the mode and age comes the project's PM, when `.project.json`
`agents` declares one (role `pm`; `<slug>-pm` first): its Telegram bot handle
(its employee ID when it has no bot), then its company identity as Flume judges
it (`flume identity manifest <pm> --json`, run by the background refresher):

- `id v1 5/6` — the identity-manifest version the PM is judged against, and how
  many of that manifest's required points it holds (v1: 1Password Identity item,
  own AAI gateway key, native Plane identity, private inbox, voice, avatar;
  Telegram is optional and not counted). `flume identity manifest <pm>` lists
  which point is missing. A PM that is not `active` gets its status appended
  (`id v1 5/6 suspended`).
- `id none` — the PM was never enrolled (no company identity), or Flume does not
  know the employee at all.
- nothing — not known yet (first prompt in a new place) or Flume did not answer.

Then two 33GOD pipeline segments, crank last:

- `🍬 3/124` — candybars registered (non-archived) for this repo / in the whole
  Candybar registry (`GET $CANDYBAR_API_URL/candybars`, default
  `http://127.0.0.1:8700`; the project is the `project:<repo>` tag, where
  `<repo>` is the main checkout's basename, exactly as `candybar ls` resolves it).
- `⚡ crank ↑3d4h ↻5m ⏳2m` — this pane's agent session has a crank v2 binding
  (`pj crank sessions`): one Candybar-clocked crank per live agent session. In a
  zellij pane the segment asks the arbiter (`crank.lua`, Redis Functions library
  `crank`) directly: `FCALL_RO crank_get` follows the pane pointer to the binding,
  pipelined with the legacy reads over a tiny builtins-only RESP2 client with a
  hard 150ms timeout, at the same endpoint `pj crank` uses (`ZCRANK_REDIS_HOST` /
  `ZCRANK_REDIS_PORT`, default `127.0.0.1:6379`). No cache, no background
  refresh: it is what Redis says right now. Outside a zellij pane it shows the
  project's crank through the cache below. When ON, three numbers follow:
  - `↑3d4h` how long the crank has been ON **without a break** (`22m`, `5h22m`,
    `3d4h`, `1w3d`): the binding's `since`. Unknown = left out.
  - `↻5m` the binding's interval.
  - `⏳2m` the countdown to the next fire: minutes, then seconds (`42s`) in the
    last minute, then `now`, read from the binding's own cron at render time, so
    it keeps counting between prompts.

  `⚠ crank stalled 25m` means the binding has not fired for max(15m,
  2×interval + 5m), or its hash expired under a live pane pointer (see the
  `33god-hub` crank sub-skill, `references/health.md`).

  The legacy engine is retired by crank v2 (PJAN-216): a pane's legacy hash is
  believed only while the engine heartbeat (`crank:engine`) is from this zellij
  session and no older than 15 minutes. Once it goes quiet the frozen hashes print
  no segment at all, never `⚠ crank stalled` and never a permanent
  `◌ crank off`; under a fresh heartbeat a legacy OFF pane reads `◌ crank off`.
  A pane with no binding and no hash is simply not watched, so it prints no segment.
  Redis unreachable (or slower than the budget) prints no crank segment either:
  an unreachable Redis is never read as OFF.

The candybar icon (shown as 🍬 above) is really the `outline/candy` icon from
[delorenj/icons](https://github.com/delorenj/icons), vendored in
`assets/prompt-glyphs/candy.svg` and printed as U+10EF0D. No Nerd Font has it,
so install the one-glyph fallback font once per machine that renders the
prompt (the terminal's machine, not the one running zellij):

```sh
scripts/build-prompt-font.py --install   # uv run; builds dist/fonts/, copies to ~/.local/share/fonts, fc-cache
```

Fontconfig then draws U+10EF0D from "pjangler Prompt Glyphs" behind any
primary font. A terminal that was already running keeps showing an empty box
until its process restarts (it reads fontconfig once at startup; a new window
of a single-instance ghostty or `alacritty msg create-window` is not enough).
`ghostty +show-face --cp=0x10EF0D` should name "pjangler Prompt Glyphs". Tabler's own codepoint (U+EF0D) is unusable: Nerd Fonts put Font
Awesome there. On a machine without the font, set
`PJ_PROMPT_CANDYBAR_GLYPH=🍫` (or any glyph) instead of living with tofu.

The candybar count, the PM's identity (and, outside a zellij pane, the project's crank) are not
computed on the prompt's critical path. They come from a small cache
(`$PJ_PROMPT_CACHE_DIR`, default `~/.cache/pjangler/prompt/`, one file per
project root, split only by in-a-zellij-pane or not) that a detached `dist/prompt-refresh.js` rewrites
when it is older than 60s, so the first prompt in a new place shows no candybar count and the
next one does (`$FLUME_BIN`, default `flume` on PATH, answers the identity). A segment whose source did not answer is omitted rather than
guessed, and a cache older than 15 minutes is not shown at all.
`PJ_PROMPT_NO_REFRESH=1` stops the background refresh.

It is a separate binary from the main CLI on purpose — the CLI loads the whole
parity rule set and takes ~52ms to boot, while this runs in ~30ms, well inside
starship's 500ms budget.

Add it to `~/.config/starship.toml` as a second, project-scoped prompt line:

```toml
format = "…$all${custom.pjangler}$line_break$character"

[custom.pjangler]
description = "pjangler project context"
when = true
shell = ["sh"]
symbol = "◆"
style = "bold purple"
# The newline lives INSIDE the conditional group, so nothing is emitted —
# not even a blank line — outside a pjangler project.
format = "(\n[$symbol $output]($style))"
command = 'exec pjangler-prompt 2>/dev/null'
```

`$line_break` must be named explicitly: it is otherwise absorbed by `$all` and
the extra line lands in the wrong place.
