# pjangler — Deployment & Release Guide

> Generated by BMAD `document-project` (deep scan) · 2026-07-13 · re-derived 2026-09-20
> "Deployment" for pjangler is two things: **publishing the npm package**, and installing the **project registry service** as one user systemd unit on each machine that uses it.

## Distribution model

`@delorenj/pjangler` is an npm package published to the public npmjs.org registry
via `publishConfig.registry` in `package.json`. Publishing uses **npm OIDC
Trusted Publishing** (GA since July 2025) — no API tokens or 2FA are required.
A GitHub Actions workflow (`.github/workflows/publish.yml`) triggered by tag
pushes (`v*`) runs `npm publish --provenance` with `NODE_AUTH_TOKEN=""` under
the `release` environment with `id-token: write` permission. The package is
installed globally (or run via `npx`) from npmjs.org. Binaries:

| Binary | Maps to | Purpose |
| --- | --- | --- |
| `pjangler`, `pj` | `dist/index.js` | CLI |
| `pjangler-mcp` | `dist/mcp-server.js` | MCP stdio server |
| `pjangler-prompt` | `dist/prompt.js` | Shell-prompt line (separate bundle so it boots in ~30ms) |

`dist/project-registry-service.js` also ships. It is not a bin — the systemd unit
written by `npm run registry:install` execs it directly.

Per prior packaging incidents (PJAN-2): this is **npm-only**, and the published tarball had gitignore/packlist landmines in the past — verify the tarball contents before publishing.

## What ships (`package.json` `files` allowlist)

Only these are included in the npm tarball:

```
dist                              # the four esbuild bundles
!dist/**/*.map                    # source maps are excluded
templates/commonproject/copier.yml    # the scaffold's interface…
templates/commonproject/template      # …and its body — nothing else from the submodule
.mise/scripts/versioning.sh       # shipped so target repos get the versioning workflow
.mise/scripts/link-agentfiles.sh
scripts/install-project-registry.mjs  # `npm run registry:install` at the install site
scripts/migrate-project-registry.mjs
src/project/registryClient.ts     # the synchronous client, consumed as source
```

`templates/hermes-agent` no longer ships: the agent template is Flume's, and
`templates/commonproject` is the repo's only submodule. The `files` list still
carries a `contracts` entry that matches nothing — the fleet contract left with
the rest of the workforce.

The parity engine reads the shipped scripts from the package root at runtime (`templateScript()`), so the `files` allowlist is load-bearing — dropping a script silently breaks the corresponding parity rule.

## Release flow

```bash
git status --short                  # must be clean
mise run release -- --dry-run       # full non-mutating release gate
mise run release                    # patch release (or pass minor / major)
```

The release task owns the only supported bump-and-publish transaction:

1. Re-exec the complete release under the pinned Node 24.6/npm 11 runtime;
   the normal Node 26/npm 12 toolchain currently cannot publish tarballs.
2. Require a clean main repo and clean initialized submodules.
3. Prove every supported submodule commit is remotely reachable and archive-safe.
4. Fetch the explicit release target (`RELEASE_REMOTE=origin`,
   `RELEASE_BRANCH=main`) and require the candidate to fast-forward it.
5. Run install, production audit, build, typecheck, tests, strict PG coverage,
   and an unauthenticated exact-tarball publish dry-run before acquiring a token.
6. Authenticate to the configured registry. For GitHub Packages, authenticate
   using the active `gh` session with a short-lived token. For npmjs.org (OIDC
   trusted publishing), no local auth is needed — publishing happens in CI.
7. Strict disposable PostgreSQL coverage uses `PGHOST`, `PGPORT`, `PGUSER`, and
   `PGPASSWORD` for the disposable instance. A release fails rather than
   skipping this database gate.
8. Bump `package.json`, regenerate `package-lock.json` with npm, verify lock
   parity, and make one `release(PJAN-<ticket>): vX.Y.Z` commit. Set
   `RELEASE_TICKET=PJAN-<number>` when neither the branch nor HEAD subject
   carries the ticket reference.
9. Build and inspect the actual tarball, run the production audit and
   tracked/package secret scan.
10. Create the commit/tag only after those gates, then atomically push both.
11. **For npmjs.org (OIDC):** the local release stops here — the tag push
    triggers the GitHub Actions `publish.yml` workflow, which runs
    `npm ci`, `npm run build`, `npm run typecheck`, `npm test`, then
    `npm publish --provenance` with `NODE_AUTH_TOKEN=""` under the `release`
    environment. The local script logs "tag pushed; GitHub Actions OIDC
    workflow will publish" and exits. For GitHub Packages, publish that exact
    `.tgz` locally and verify the new registry version. If the atomic push
    fails locally, rerun with `--resume-push`.

`prepublishOnly` remains a defense-in-depth build/template/secret gate.
`PJANGLER_VERSION` is read from `package.json` at runtime, so `pj --version`
and MCP `serverInfo` match the published package without a separate source bump.

If publication fails after the atomic git push, `mise run release -- --publish-current`
is a strict retry path. It refuses unless the clean HEAD and its annotated version tag
are already present on the configured remote main ref, reruns the gates, inspects a
new exact tarball, and confirms the registry version is still unused. For npmjs.org
(OIDC), the retry path skips local publish and directs the user to re-run the GitHub
Actions workflow from the Actions UI.

### Pre-publish checklist

1. `npm run typecheck` clean.
2. `npm run check:lock` and `npm test` green.
3. `mise run version:check` — versioned files in parity.
4. Run the PG harness in strict mode against a disposable endpoint:
   `PJANGLER_REQUIRE_DISPOSABLE_POSTGRES=1 node tests/pg-registry-regressions.mjs`.
5. Inspect the actual `npm pack --json` tarball (not `--dry-run`) and confirm the
   six paths the release script requires: `package.json`, `dist/index.js`,
   `dist/mcp-server.js`, `templates/commonproject/copier.yml`, and both
   `.mise/scripts/*.sh` (PJAN-2 guard).
6. Confirm `templates/commonproject` is populated and remotely reachable.
7. Confirm the release branch is a fast-forward of the configured remote main.

## CI

`.github/workflows/` contains Claude Code automation and the OIDC publish pipeline:

- `claude.yml` — Claude Code interactive workflow
- `claude-code-review.yml` — automated PR code review
- `publish.yml` — npm OIDC Trusted Publishing workflow; triggers on tag push (`v*`),
  runs `npm ci`, `npm run build`, `npm run typecheck`, `npm test`, then
  `npm publish --provenance` with `NODE_AUTH_TOKEN=""` under the `release`
  environment (`id-token: write`, `contents: read`)

Build, test, and the release commit/tag are run locally via the commands above;
publishing to npmjs.org happens in CI via the `publish.yml` workflow triggered by
the tag push.

## Runtime dependencies at the install site

- **Node ≥ 24** (ESM) — `package.json` `engines` pins it.
- **`copier`** (Python) on `PATH` for any scaffolding/apply operation — `uv tool install copier`. Missing copier is handled gracefully (surfaced as an actionable error, not a crash) but blocks the `copier.copy.commonproject` action.
- **`git`** for repo-root detection and submodule operations.
- **PostgreSQL** + **`systemctl --user`** for the project registry service.
- Optional: **`op`** (1Password CLI) for `.env.op` injection.

## The registry service

Every read that is not "the manifest in front of me" goes through the singleton
project registry service on `http://localhost:8764`. Install it once per machine:

```bash
npm run build
npm run registry:install
```

That writes `~/.config/systemd/user/pjangler-project-registry.service`
(`Restart=on-failure`, the local PostgreSQL Unix socket, database `33god`, peer
authentication, **no credential values in the unit**), verifies it with
`systemd-analyze --user verify`, then enables and restarts it. `PJ_REGISTRY_URL`
points a client somewhere else. Migration from the legacy YAML and the full
endpoint contract are in [`project-registry.md`](./project-registry.md).

## Consuming pjangler from an agent (MCP)

Register `pjangler-mcp` as an MCP server (stdio). Agents should start with `pjangler_list_capabilities`, then use the audit → migrate workflow. Preview is the default across all 12 tools: writes require `apply: true` and each external effect requires `live: true` plus an explicit positive opt-in, so an agent cannot create a board or overwrite files by accident. No tool provisions an agent — that is `flume`.
