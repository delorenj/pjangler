# PJAN-70 — MCP cancellation and subprocess deadlines

## Contract

All four mutation tools (`pjangler_migrate_project`, `pjangler_bootstrap_33god_project`, `pjangler_project_init`, `pjangler_run_recipe`) accept an integer `timeoutMs`: default **120000 ms**, range **1–600000 ms**. The SDK request signal is captured before handler work. Both read and mutation handlers share an operation-local, monotonic deadline across preflight, registry snapshots, lifecycle dispatch and subprocesses. Lifecycle contexts expose `signal`, `deadlineMs`, and `assertActive`. A pre-aborted request cannot start work. Stops return `isError: true` with distinct stable `MCP operation cancelled` or `MCP operation deadline-exceeded` reasons; stopped work cannot be reported as success. The SDK client may locally reject a cancelled call rather than receive its server-side result.

`runChild` uses asynchronous `spawn` (`shell: false`), bounded combined raw stdout/stderr bytes (16 MiB default), decodes each complete stream as UTF-8 after capture so split multibyte sequences remain intact, and starts a fresh POSIX process group. It sends SIGTERM to the group on stop, escalates to SIGKILL after **500 ms** even if the leader has exited but descendants hold stdio, and settles at most **100 ms** after escalation. Spawn/kill failures remain visible; overflow remains a distinct diagnostic. A shorter child-local timeout, including inside an MCP operation, terminates only that group and returns an ETIMEDOUT child outcome so optional probes may recover; it never marks a still-live shared deadline exceeded. Only actual shared request cancellation or deadline expiry stops the entire MCP operation, including when it occurs during local child cleanup. Windows lacks a process-tree guarantee and needs a separate implementation before claiming parity. This change does **not** promise transactional rollback of writes already completed before cancellation or compensation for external services.

## Reachability inventory

MCP handlers (`src/mcp-server.ts`) execute inside `withOperation` and request-local registry snapshots. Mutation paths dispatch project planning/initialization, recipe lifecycle and parity migration; read handlers use the same operation boundary. Their reachable processes now use cancellable `runChild` or an asynchronous operation-specific branch:

- Project preflight/version probe, Copier apply, project Git, operator name and project registry read/write: `src/lifecycle/preflight.ts`, `src/project/{index,registryClient}.ts`, `src/recipes/ProjectRecipe.ts`.
- BMAD installer/version/npx, provider/px smoke checks, git/index/skill roots, and g33 module resolution: `src/parity/{rules,skill-roots,skills}.ts`, `src/bmad/{companion,update-scope}.ts`.
- Provider secret lookup and identity/rename/import actions and postcondition probes: `src/project/{identity,rename,import}.ts`. Board query and identity/rename HTTP helpers share the cancellation contract when called inside an operation: `src/project/{boardQuery,identity,rename}.ts`. These helpers are not directly registered MCP tools today; their isolated HTTP tests invoke production functions from a private recipe to exercise the operation boundary.
- Read-side activity/description, notebook Git evidence, entropy, hooks/projector and summarizer: `src/describe/activity.ts`, `src/notebook/{git-evidence,entropy,hooks,summarizer,module}.ts`.
- The project external-effect tail reaches `NotebookRecipe.applyExternal` → `NotebookModule.provisionResolved` → `OpenNotebookClient`. Its auth probe, every request and every response-body read use `withHttpResponse` in `src/lifecycle/operation.ts`. The helper composes the shared operation signal with local HTTP/composite-hook limits, checks activity before dispatch and after headers/body, and aborts unread bodies on exit. The original deadline never resets across probes, requests or pages. Stops bypass auth fallback and provider error normalization; reconciliation, binding and commit boundaries also check activity. Standalone notebook hooks retain their own deadline and `NotebookError(TIMEOUT)` category outside MCP.

A source-wide `spawnSync|execSync|execFileSync` inventory retains synchronous calls in CLI-only `src/index.ts`, crank and prompt-refresh, plus CLI fallbacks in dual-use modules. Dual-use MCP paths use asynchronous wrappers; `registryRequest` refuses an uncached synchronous MCP service call rather than blocking, and MCP primes its snapshot first. Registry HTTP runs in a `runChild`-managed Node process; its headers and body waits are stopped by process-group cleanup. The remaining direct fetch sites in crank and prompt-refresh are outside the MCP call graph and were not changed. Parity, recipe and migration catch/loop boundaries check the active operation before subsequent phases/writes, including installer completion and migration fallback. This inventory describes the current reachable routes, not a promise that a newly added entrypoint automatically inherits their discipline.
